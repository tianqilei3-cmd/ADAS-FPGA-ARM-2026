记录日期：2026-10-10，北京时间。交接对象：FPGA队友、ARM后续开发者及接手本项目的AI。

本次重新读取了模型评估报告、训练记录、10月10日两次视频演示日志，并抽查了最新输出视频的红灯和绿灯画面。下文明确区分已完成、尚未验证和建议方案；建议接口还没有实现为板间协议。

## 1. 给队友的进度摘要

ARM侧已完成两个YOLOv8n检测模型的PC训练和官方视频离线演示：一个检测车辆、行人、两轮车和交通灯位置，另一个检测红、黄、绿、熄灭灯状态。官方灯色微调已完成15轮，目前最佳权重来自第12轮。

10月10日已完整处理官方 `113539` 视频，共2315帧、约77.17秒内容，完成386次双模型推理，生成带检测框视频及结构化日志。车辆、行人、两轮车和红绿灯均有模型输出；抽查确认红绿灯可以检出，但仍有灯头漏检和框范围偏小的问题。

当前阶段是“PC视觉原型已跑通”。本轮没有完成Orange Pi／RK3566上的新模型部署，也没有验证FPGA与ARM实时图像传输、结果回传和HDMI／LED闭环。FPGA队友可以先推进单路视频链路、帧号同步、固定结果解析及显示叠加，不必等待模型效果完全优化。

## 2. 分工与硬件背景

用户负责ARM侧：数据准备、模型训练、目标识别、规则逻辑、后续板端推理及结果回传。队友负责FPGA侧：视频采集、预处理、缓存、传输、显示叠加、按键及LED等。

既有项目资料中的目标平台为盘古50K／PGL50H FPGA与Orange Pi 3B／RK3566。具体板卡、连接方式、驱动和高速接口能否使用，仍需双方在实物上确认。本次未查询队友的最新FPGA工作，因此不能据本文件认定FPGA端已经完成或尚未完成某项任务。

去年资料是车牌识别作品，可参考其视频输入、DDR、缩放、拼接、显示和ARM程序框架；其中的车牌RKNN模型不等于今年ADAS模型。

## 4. 训练成效：要按验证场景分别解释

### 4.1 道路四类模型

数据：BDD100K四类子集，5000张训练图、1000张验证图；当前模型640输入，第4阶段20轮。

| 指标／类别 | mAP50或AP50 | 召回率 |
|---|---:|---:|
| 总体 | 32.65% | 33.28% |
| vehicle：车辆 | 62.87% | 63.12% |
| person：行人 | 35.63% | 35.01% |
| traffic_light：交通灯位置 | 25.55% | 24.19% |
| two_wheeler：两轮车 | 6.57% | 10.81% |

总体mAP50–95为15.74%。车辆目前相对较强，两轮车较弱。上述指标来自BDD验证集，不是官方视频的逐帧准确率，也不是比赛现场成绩。

类别映射：0=traffic_light，1=vehicle，2=two_wheeler，3=person。车辆合并car／bus／truck；两轮车合并bike／motor；行人类包含person／rider。

### 4.2 灯色模型：源数据与官方场景存在明显差距

| 验证内容 | 官方微调前 | 官方微调后（最佳权重） |
|---|---:|---:|
| 官方验证总体mAP50 | 3.11% | 17.17% |
| 官方验证总体mAP50–95 | 0.52% | 7.74% |
| 官方红灯AP50 | 7.12% | 3.86% |
| 官方绿灯AP50 | 2.20% | 47.65% |
| 官方黄灯AP50 | 0.00% | 0.00% |
| S²TLD原验证集总体mAP50 | 90.71% | 88.33% |

官方总体mAP50提高14.06个百分点，主要体现为绿灯改善；红灯未改善，当前召回率为6.25%，绿灯召回率为55%。原S²TLD总体mAP50下降约2.38个百分点。

官方val只有40张有效图片，其中红灯16个、绿灯20个、黄灯1个，没有可靠off标注；黄灯数据不足，无法可靠评价这一类。原S²TLD的90%以上指标不能直接代表官方视频能力。

灯色模型类别映射：0=red，1=yellow，2=green，3=off。off表示明确熄灭；unknown表示无法判断，是逻辑状态，不是训练类别。

## 7. FPGA队友可以立即推进的工作

以下为协作建议，不是已完成事项。无需等待下一轮训练结束。

| 顺序 | FPGA侧工作 | ARM侧配合／通过条件 |
|---|---|---|
| 1 | 冻结单路视频直通：输入、DDR、输出 | 明确实际分辨率、像素格式、帧率及接线；当前PC视频分辨率不强制作为传输规格 |
| 2 | 确定图像发送与控制／结果回传通道 | 双方核实板卡接口与驱动；现阶段不假定PCIe或其他高速接口已打通 |
| 3 | 加帧号、帧长、通道号及错误状态 | ARM收到测试图后保存原帧，核对颜色、行顺序、完整性及帧号 |
| 4 | 用固定模拟结果实现框及状态叠加 | 可用随包detections.jsonl作为字段与坐标参考；传输打包格式需另行确定 |
| 5 | 做结果过期／超时处理 | 过期框不叠到不对应的画面；超时选灯状态置unknown，不延续旧GO |
| 6 | 接入按键、LED及状态回读 | FPGA按键事件送到ARM，ARM计算状态后回传；清楚区分检测结果、导航方向和告警 |
| 7 | 单路推理闭环，再扩展多路 | ARM板端模型运行后联调；测量端到端延迟、丢帧与连续运行稳定性 |

红绿灯模型要保留颜色输入，不能把灰度图直接替代其训练时的彩色输入。FPGA可另输出灰度／边缘用于车道算法，同时保留原彩色画面或合适的彩色ROI给目标与灯色模型。若硬件改变色序、亮度、裁剪和缩放，需在ARM输入处理中统一并重新验证。

## 8. 接口字段草案：用于双方讨论，尚未冻结或实现

当前真实程序输出的是本地JSONL文件；下表是建议的板间语义字段。字节布局、字节序、最大框数、置信度编码、CRC、带宽、超时阈值都还待双方确定。

### 8.1 FPGA → ARM

| 字段 | 目的／约定建议 |
|---|---|
| protocol_version | 协议版本 |
| camera_id、frame_id | 视频通道与原始帧号；回传必须沿用该帧号 |
| capture_timestamp | 采集时间，时钟单位与双方时钟关系待定 |
| width、height、stride_bytes | 原图尺寸、每行字节数 |
| pixel_format、payload_length | 明确RGB／BGR、RGB888／RGB565等及图像长度 |
| roi_origin、roi_size | 传裁剪图时保留其在原图的来源位置和尺寸 |
| button_event／mode | 模拟车道、移动状态及模式切换输入；不当作模型真值 |

### 8.2 ARM → FPGA

| 字段 | 目的／约定建议 |
|---|---|
| protocol_version、camera_id、frame_id | 匹配输入帧，避免结果错位 |
| source_width、source_height | 框坐标使用的原图坐标系 |
| result_valid、age／timestamp | 判断结果是否可用及是否过期 |
| detections[] | 每框包含model_id、class_id、confidence、x1、y1、x2、y2 |
| selected_light_state | unknown／red／yellow／green／off，与所有灯框列表分开 |
| action | UNKNOWN／STOP／GO／CAUTION，与导航左／直／右分开 |
| alarm | none／RED_LIGHT_VIOLATION等；后续事件尚未实现 |
| lane／navigation／valid_flags | 自动车道与导航未实现时明确标无效；当前lane是人工模拟输入 |

两个模型的class_id存在重叠，必须带model_id或统一类别映射：道路模型0是交通灯位置，灯色模型0是红灯，不能合并后只传裸class_id。

现有日志仅有name，没有model_id字段；它通过roads与lights两个数组区分模型。这是已有事实，不要把草案字段写成当前代码已经提供。

显示缩放示例：若把完整1920×1080原图缩放到同宽高比的1280×720显示区域，框坐标乘2/3；若有黑边或四画面窗口，还要加显示区域偏移。具体硬件分辨率确定后再实现，不能直接把模型640输入尺寸当显示坐标。

建议先固定上述语义，再选传输封装。低带宽控制与完整图像传输应分别测量带宽需求；现有PCJSON日志只是参考格式，尚未验证能直接用于任何板间链路。
